设备是小米 13（`fuxi`），HyperOS 3、版本号 `OS3.0.309.0.WMCCNXM`、内核 `5.15.194`、安全补丁 2026-08-01。目标只有一个：绕开 168 小时的等待，把 BL 解掉。

先说结论：最后还是靠一支 2026 年的国产工具，用临时内核 root 把一份工程 `abl` 写进两个槽，再进 fastboot 执行解锁。

这条路前面试了三个方案，两个成品工具当场失败，一个降级方案读到一半就停了。写下来是因为每一步的「为什么不行」都比「怎么做」有用。

## 起点：309 和一份换掉的封装

在手的小米 13（`fuxi`）是 HyperOS 3、版本号 `OS3.0.309.0.WMCCNXM`，内核 `5.15.194`，安全补丁 2026-08-01。

解锁 BL 的常规定速是「等 168 小时 + 答题」，慢但确定。要绕开它，社区有两种思路：申请时用伪造的设备信息骗过校验，或者把旧版「设置」换回系统分区、让申请入口退回没有封装的版本。

两个成品工具走的是第二种：HyperSploit 和 MlgmXyysd 的 Bypass。**都失败了**，而且不是用法不对。它们都是 2023 年针对旧封装写的，309 把 RSA 封装换了，客户端没有对应私钥，工具自己就报「patched」或者参数异常。它们给出的唯一绕法就是「回滚旧版 Settings」。

## 回滚 Settings 撞上的三重墙

这条路在 309 上也断了，而且是三道一起断：

1. 旧包的 `versionCode` 是 34，系统里装的是 36。`pm install -d`、`-r -d` 全被「降级」拒掉。
2. 想改版本号就动了 APK，签名跟着变；而设置是系统应用，只认官方签名，改完装进去报 `are not updateable`。
3. 拿到 root 直接覆盖呢？`/system_ext` 是 dm-verity 保护的只读分区。root shell 里 `cmd package` 连不上 package 服务，也没法走「让系统自己装」。

到这一步设备还是原厂态、能正常开机，没砖。停下比硬来重要。

## 一份零写入的方案，和一份赌主板的方案

停下来之后重新查资料，看到两条完全不同的路。

**一条是把 `selinux=permissive` 塞进启动参数。** 具体是 `fastboot oem set-gpu-preemption-value ... selinux=permissive`，然后 `fastboot continue`，再用一串 `service call` 改内存里的系统属性、重启 zygote。

它的好处很硬：**不写任何分区**，参数在内存里，重启就没了。最坏结果是 `getprop` 打出来还是 309、属性没改成，风险上限就是白折腾一次。坏处也明确：作者实测的机器是 HyperOS 2，评论区已经有人说「更新到 2026 补丁后命令不生效」。

**另一条是 9008 免授权深刷。** 走这条路之前有个判据必须先读，因为它不是对所有机器都成立：

> 8Gen2 只支持 2026 年 2 月补丁及以下用工具解锁；更高版本如果不是铠侠闪存、且 9008 未熔断，才走 9008 深刷。

我们是 9 月的补丁，先查闪存：`THGJFJT2T85BAT0C`，**铠侠**。

于是 9008 的结论变成：能走，但属于「没过保修就直接搏，砖了送售后换主板」。对一台刚用顺手的主力机，这是要单独做决定的代价，不是顺手试一下。

顺序就排成：先试零写入的，不行再看要不要赌。

## 正解：写 abl，但只写 abl

后来查到 `JiGuang-8Gen2-tool`。它和前面两个工具不是一类东西：

- 明确支持 `fuxi`；
- 明确说铠侠也能用；
- 流程是 `push` 自带 `abl` + `preload` 提权 → fastboot 设 permissive → `continue` 回系统 → root 下 `dd` 写 `abl_a`/`abl_b` → 灌解锁镜像。

它写的是 **abl 分区**，不是 EDL 深刷。abl 是引导加载程序本身，`dd` 两条命令就能换回来，所以砖的风险比 9008 低一个量级；而且解锁完成之后，系统更新会把官方 abl 换回去，工程 abl 的使命就结束了——解锁状态存在别的分区，不依赖它。

代码是酷安 `@御坂114515号` 的二改版本，作者信息留在脚本抬头里。包从 GitHub 拿，167 MB 的 7z，解开 1.4 GB，里面是有 `images/fuxi`、`images/sheng` 两个机型目录的完整工具链。

## 卡住的两次都不是技术问题

第一次跑停在「要求干净的 Enforcing」。之前手动提权把 SELinux 留在了 `enforce=0`，工具据此认为环境不干净，直接退出。

处置很简单：重启一次。abl 还没动，重启是安全的；回到系统后重新跑，这次 `enforce=1`，它才往下走。

第二次是驱动。工具包只带 `adb.exe` 和 `fastboot.exe`，不带驱动，Win11 也不自带。设备管理器里带着黄色感叹号的时候，`adb devices` 是空的。装 MiFlash（自带小米 USB / QDLoader 驱动）之后才认。这里有个反直觉的点：**别用 Zadig 把设备换成 WinUSB**，fastboot 会不稳。

节奏上还有一条：脚本从 push 到写 abl 是一整条链，中途手动重启会断在当前状态。它会在屏幕上要求「按电源 + 音量下进 fastboot」，那一步照做，然后什么都别碰。

## 双槽要都写

工具在 `dd` 那一步会写 `abl_a` 和 `abl_b` 两条。

只写一个槽不会立刻出事，但另一槽还是官方 abl，解锁后切槽就会遇到两个槽的引导不一致。要手敲的话：

```sh
ls -l /data/local/tmp/abl.elf
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_a bs=4096 conv=fsync
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_b bs=4096 conv=fsync
sync
```

先 `ls` 确认文件在（200 多 KB），有再 `dd`。

## 收尾

解锁成功之后，`flash.locked=0`、`unlocked: yes`、橙色警告、开机 5 秒等待。数据被清空。

回头看这四条路的排序其实是按「写坏了能不能救」排的：零写入 > 写 abl > EDL 深刷。成品工具失效不代表思路失效，它只是证明**先判断这次要动哪个分区**比先找一个能跑的工具重要。

还有一件事得写在这：解锁状态是持久的，别随手锁回去，锁回去再解就要从头走一遍。

## 常见问题

**Q：OS3.0.309 上还能用 HyperSploit 或 Bypass 吗？**
不能。这两个工具是针对 2023 年旧封装的，309 换了 RSA 封装，客户端没有对应私钥，跑起来只会报 `patched` 或参数异常。

**Q：不敢碰 9008，只写 abl 安全吗？**
比 9008 低一个量级。abl 是引导程序本身，`dd` 两条命令就能换回来；解锁完成后系统更新还会把官方 abl 写回去，解锁状态不依赖它。

**Q：解锁会清数据吗？要等多久？**
会，解锁必然清空 data，先备份。等待时间取决于方法：工程 abl 这条路从开始到完成大约十几分钟，外加首次开机和格式化。
