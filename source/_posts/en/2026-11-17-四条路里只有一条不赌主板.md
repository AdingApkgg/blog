Let me start with the conclusion: in the end it came down to a 2026 domestic tool that used a temporary kernel root to write an engineering `abl` into both slots, then entered fastboot to perform the unlock.

Three approaches were tried before this one: two finished tools failed on the spot, and a downgrade approach stopped halfway through. I'm writing it up because the "why it doesn't work" at each step is more useful than the "how to do it."

## Starting point: 309 and a swapped wrapper

The Xiaomi 13 (`fuxi`) on hand runs HyperOS 3, build number `OS3.0.309.0.WMCCNXM`, kernel `5.15.194`, security patch 2026-08-01.

The standard route to unlocking the bootloader is "wait 168 hours + answer a quiz" — slow but certain. To get around it, the community has two ideas: spoof device info during the application to fool the check, or push an old version of Settings back into the system partition so the application entry point reverts to a version without the wrapper.

Both finished tools take the second approach: HyperSploit and MlgmXyysd's Bypass. **Both failed**, and not because they were used wrong. Both were written in 2023 against the old wrapper; 309 swapped out the RSA wrapper, the client has no matching private key, and the tools themselves report "patched" or a parameter exception. The only workaround they offer is "roll back to the old Settings."

## The three walls hit by rolling back Settings

This route is also dead on 309, and all three break at once:

1. The old package's `versionCode` is 34; the one installed on the system is 36. `pm install -d` and `-r -d` are both rejected as a "downgrade."
2. Changing the version number means touching the APK, and the signature changes with it; but Settings is a system app and only accepts the official signature, so installing the modified build throws `are not updateable`.
3. What about getting root and overwriting it directly? `/system_ext` is a read-only partition protected by dm-verity. In a root shell, `cmd package` can't reach the package service, and there's no way to "let the system install it itself" either.

At this point the device is still stock and boots normally — not bricked. Knowing when to stop matters more than forcing it.

## A zero-write plan, and a plan that bets the motherboard

After stopping, I went back to researching and found two completely different routes.

**One is to stuff `selinux=permissive` into the boot parameters.** Specifically `fastboot oem set-gpu-preemption-value ... selinux=permissive`, then `fastboot continue`, then a string of `service call` to change the system properties in memory and restart zygote.

Its advantage is solid: **it writes no partition at all** — the parameters live in memory and vanish on reboot. The worst case is that `getprop` still prints 309 and the properties don't change; the ceiling of risk is one wasted attempt. The downside is equally clear: the author tested on a HyperOS 2 machine, and people in the comments already say "the commands stop working after the 2026 patch."

**The other is a 9008 deep flash without authorization.** Before taking this route there's a criterion you have to read first, because it doesn't hold for every device:

> 8Gen2 only supports tool-based unlocking on the February 2026 patch and below; for higher versions, only if the flash storage isn't Kioxia and 9008 isn't blown, do you go the 9008 deep-flash route.

We're on the September patch, so check the flash storage first: `THGJFJT2T85BAT0C` — **Kioxia**.

So the 9008 conclusion becomes: it's possible, but it falls under "if you're still in warranty, just gamble; if it bricks, send it to service for a motherboard swap." For a daily driver you've just gotten comfortable with, that's a cost you have to decide on separately, not something you try on a whim.

So the order became: try the zero-write one first, and only then consider whether to gamble.

## The right answer: write abl, but only abl

Later I found `JiGuang-8Gen2-tool`. It's not the same kind of thing as the previous two tools:

- Explicitly supports `fuxi`;
- Explicitly says Kioxia works too;
- The flow is: `push` ships its own `abl` + `preload` for privilege escalation → set permissive in fastboot → `continue` back into the system → under root, `dd` writes `abl_a`/`abl_b` → flash the unlock image.

What it writes is the **abl partition**, not an EDL deep flash. abl is the bootloader itself, and `dd` two commands bring it back, so the brick risk is an order of magnitude lower than 9008; and once unlocking is done, a system update will restore the official abl, ending the engineering abl's mission — the unlock state lives in another partition and doesn't depend on it.

The code is a modified version by `@御坂114515号` on Coolapk, with the author info left in the script header. The package comes from GitHub: a 167 MB 7z that unpacks to 1.4 GB, containing a full toolchain with two device directories, `images/fuxi` and `images/sheng`.

## Neither of the two stalls was a technical problem

The first run stopped at "requires clean Enforcing." An earlier manual privilege escalation had left SELinux in `enforce=0`, and the tool took that as an unclean environment and exited immediately.

The fix was simple: reboot once. abl hasn't been touched yet, so rebooting is safe; after getting back into the system, run it again — this time `enforce=1`, and only then does it proceed.

The second time, it was the drivers. The toolkit only ships `adb.exe` and `fastboot.exe`, no drivers, and Windows 11 doesn't include them either. While Device Manager is showing a yellow exclamation mark, `adb devices` is empty. It only gets recognized after installing MiFlash (which bundles the Xiaomi USB / QDLoader drivers). Here's the counterintuitive part: **don't use Zadig to swap the device over to WinUSB** — fastboot becomes unstable.

One more thing about pacing: the script is a single chain from push to writing abl, and a manual reboot midway leaves it stuck at the current state. It will ask on screen to "hold Power + Volume Down to enter fastboot" — do that step, then don't touch anything.

## Both slots have to be written

At the `dd` step the tool writes both `abl_a` and `abl_b`.

Writing only one slot won't blow up right away, but the other slot still holds the stock abl, and once you're unlocked, switching slots runs into inconsistent boot images between the two. If you're typing it by hand:

```sh
ls -l /data/local/tmp/abl.elf
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_a bs=4096 conv=fsync
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_b bs=4096 conv=fsync
sync
```

First `ls` to confirm the file is there (200-something KB), and only then `dd`.

## Wrapping up

After a successful unlock: `flash.locked=0`, `unlocked: yes`, the orange warning, and a 5-second wait at boot. Data is wiped.

Looking back, the ordering of those four routes was really by "can it be rescued if it bricks": zero writes > writing abl > deep EDL flash. A ready-made tool failing doesn't mean the approach fails; it only proves that **deciding which partition you're touching this time** matters more than finding a tool that runs.

One more thing has to go here: the unlocked state is persistent — don't casually lock it back, because locking it back means going through the whole thing again from the start.
