端末は Xiaomi 13（`fuxi`）で、HyperOS 3、ビルド番号 `OS3.0.309.0.WMCCNXM`、カーネル `5.15.194`、セキュリティパッチ 2026-08-01。目的はただ一つ、168 時間の待機を回避して BL を解除することだ。

結論から言う。最終的には 2026 年の国産ツール一本に頼り、一時的なカーネル root でエンジニアリング用の `abl` を 2 つのスロットに書き込み、fastboot に入って解除を実行した。

ここに至るまでに 3 つの案を試した。完成品ツール 2 つはその場で失敗し、ダウングレード案は途中まで読んだところで止まった。書き残すのは、各段階の「なぜダメか」が「どうやるか」より役に立つからだ。

## 起点：309 と差し替えられたパッケージ

手元の Xiaomi 13（`fuxi`）は HyperOS 3、ビルド番号 `OS3.0.309.0.WMCCNXM`、カーネル `5.15.194`、セキュリティパッチ 2026-08-01。

BL 解除の通常ルートは「168 時間待つ + クイズに答える」で、遅いが確実だ。これを回避するにはコミュニティに 2 つの発想がある。申請時に偽装した端末情報で検証を騙すか、旧版の「設定」をシステムパーティションに戻して申請入口をパッケージ化前のバージョンへ巻き戻すか。

完成品ツール 2 つは後者を採る。HyperSploit と MlgmXyysd の Bypass だ。**どちらも失敗した**し、使い方が悪いわけでもない。どちらも 2023 年に旧パッケージ向けに書かれたもので、309 で RSA パッケージが差し替えられ、クライアントに対応する秘密鍵がないため、ツール自身が「patched」やパラメータ異常を吐く。彼らが示す唯一の回避策は「旧版 Settings へのロールバック」だ。

## Settings のロールバックがぶつかった三重の壁

この道も 309 では途絶えた。しかも三つ同時に。

1. 旧パッケージの `versionCode` は 34 で、システムに入っているのは 36。`pm install -d`、`-r -d` はすべて「ダウングレード」として弾かれる。
2. バージョン番号を変えようとすれば APK に手を入れることになり、署名も変わる。しかも設定はシステムアプリで公式署名しか認めないため、書き換えてインストールすると `are not updateable` が出る。
3. root を取って直接上書きする手はどうか。`/system_ext` は dm-verity で保護された読み取り専用パーティションだ。root シェルでは `cmd package` が package サービスに繋がらず、「システム自身にインストールさせる」こともできない。

ここまでで端末はまだ純正状態のまま、正常に起動でき、文鎮化していない。無理押しより立ち止まることが大事だ。

## 書き込みゼロの案と、マザーボードを賭ける案

立ち止まってから資料を調べ直すと、まったく別の 2 つの道が見えた。

**一つは `selinux=permissive` を起動パラメータに押し込む方法。** 具体的には `fastboot oem set-gpu-preemption-value ... selinux=permissive`、続いて `fastboot continue`、さらに `service call` の連なりでメモリ上のシステムプロパティを書き換え、zygote を再起動する。

利点は強烈だ。**どのパーティションにも書き込まない**。パラメータはメモリ上にあり、再起動で消える。最悪の結果は `getprop` を叩いても 309 のままでプロパティが変わらないことで、リスクの上限は一度空振りするだけだ。欠点も明確で、作者が実機で試したのは HyperOS 2 であり、コメント欄にはすでに「2026 パッチに更新したらコマンドが効かない」という声がある。

**もう一つは 9008 の認可不要な深層書き込み。** この道を行く前に必ず読むべき判断基準がある。すべての機種で成り立つ話ではないからだ：

> 8Gen2 は 2026 年 2 月パッチ以前のみツールでの解除に対応する。それより新しい版では、キオクシア製フラッシュでなく、かつ 9008 がヒューズ未切断の場合に限り 9008 深層書き込みに進む。

こちらは 9 月のパッチだ。まずフラッシュを確認する：`THGJFJT2T85BAT0C`、**キオクシア**。

すると 9008 の結論はこうなる。行けるが、「保証期間内ならそのまま賭ける、文鎮化したらサポートに送ってマザーボード交換」の類だ。ちょうど使い慣れてきたメイン機にとって、これは気軽に試す話ではなく、単独で判断すべきコストだ。

順番はこうなった。まず書き込みゼロのものを試し、ダメなら賭けるかどうかを考える。

## 正解：abl を書く、ただし abl だけ

その後 `JiGuang-8Gen2-tool` を調べ当てた。これは前の 2 つのツールとは種類が違う：

- `fuxi` を明示的にサポート；
- キオクシアでも使えると明言；
- 手順は `push` が同梱する `abl` + `preload` で権限昇格 → fastboot で permissive 設定 → `continue` でシステムに戻る → root で `dd` により `abl_a`/`abl_b` を書き込み → 解除イメージを流し込む。

書き込むのは **abl パーティション**で、EDL 深層書き込みではない。abl はブートローダーそのもので、`dd` の 2 コマンドで戻せるため、文鎮化リスクは 9008 より一桁低い。しかも解除が完了すればシステム更新が公式 abl を書き戻し、エンジニアリング abl の役目は終わる——解除状態は別のパーティションに保存され、これに依存しない。

コードは酷安の `@御坂114515号` による二次改変版で、作者情報はスクリプト冒頭に残されている。パッケージは GitHub から取得した 167 MB の 7z で、展開すると 1.4 GB、中には `images/fuxi`、`images/sheng` という 2 つの機種ディレクトリを含む完全なツールチェーンが入っている。

## つまずいた 2 回はいずれも技術的な問題ではない

1 回目は「クリーンな Enforcing を要求」で止まった。以前に手動で権限昇格した際に SELinux を `enforce=0` のままにしていたため、ツールは環境がクリーンでないと判断してそのまま終了した。

対処は簡単で、一度再起動するだけ。abl はまだ触っていないので再起動は安全だ。システムに戻って再実行すると、今度は `enforce=1` で、そこでようやく先へ進んだ。

二つ目はドライバだ。ツールキットには `adb.exe` と `fastboot.exe` しか入っておらず、ドライバは同梱されていないし、Win11 にも標準で入っていない。デバイスマネージャーに黄色い感嘆符が付いている状態では、`adb devices` は空だ。MiFlash（小米 USB / QDLoader ドライバを同梱）を入れて初めて認識される。ここには直感に反する点がある：**Zadig でデバイスを WinUSB に置き換えるな**、fastboot が不安定になる。

テンポについてももう一つ：スクリプトは push から abl 書き込みまで一本のチェーンで、途中で手動再起動するとその状態で止まる。画面に「電源 + 音量下を押して fastboot に入れ」と要求されるので、その手順だけは従い、あとは何も触らない。

## 両方のスロットに書く

ツールは `dd` のステップで `abl_a` と `abl_b` の二つを書き込む。

片方のスロットだけ書いてもすぐには問題にならないが、もう片方のスロットは公式 abl のままで、アンロック後にスロットを切り替えると二つのスロットのブートが不一致になる。手で打つなら：

```sh
ls -l /data/local/tmp/abl.elf
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_a bs=4096 conv=fsync
dd if=/data/local/tmp/abl.elf of=/dev/block/by-name/abl_b bs=4096 conv=fsync
sync
```

先に `ls` でファイルがあること（200 数 KB）を確認し、あってから `dd`。

## 仕上げ

アンロックに成功すると、`flash.locked=0`、`unlocked: yes`、オレンジ色の警告、起動時の 5 秒待機。データは消去される。

振り返ると、この四つの道の並びは実は「書き壊しても救えるか」で決めていた：ゼロ書き込み > abl 書き込み > EDL 深層書き込み。完成品ツールが使えなくなっても考え方は使えなくなるわけではない。それはただ、**まず今回どのパーティションを触るのかを判断する**ことが、動くツールを先に探すことより重要だと証明しているだけだ。

もう一つここに書いておくべきことがある：アンロック状態は永続的だ。気軽にロックし直すな、ロックし直してから再度アンロックするには最初からやり直しになる。

## よくある質問

**Q：OS3.0.309 でも HyperSploit や Bypass は使える？**
使えない。この二つのツールは 2023 年の旧ラッピング向けで、309 は RSA ラッピングに変わっており、クライアントに対応する秘密鍵がない。実行しても `patched` かパラメータ異常を報告するだけだ。

**Q：9008 は怖い、abl を書くだけなら安全？**
9008 より一桁低い。abl はブートローダーそのもので、`dd` の二つのコマンドで戻せる。アンロック完了後はシステムアップデートで公式 abl が書き戻されるし、アンロック状態はそれに依存しない。

**Q：アンロックするとデータは消える？どれくらい待つ？**
消える。アンロックは必ず data を消去するので先にバックアップを。待ち時間は方法次第だ：エンジニアリング abl の道なら開始から完了まで十数分、加えて初回起動とフォーマットがかかる。
