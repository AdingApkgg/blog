セーブデータの本体はずっと一台の Windows のストレージサービスに置かれていて、ゲームのソースと同じバケットの隣にある。移す理由は複雑ではない。そのバックエンドは GUI を開いた Windows 上でしか動かせず、しかもユーザーごとのセーブデータはどれも完全な一份で、同じバイト列が何度も保存されている。

目標は本体をオブジェクトストレージ内の共有 CAS へ移すことだ。オブジェクト名は `<sha256>.bin` そのもので、ユーザーをまたぎ、作品をまたぎ、同じバイト列は一つだけ残す。業務データベースは引き続き「誰がどれを所有するか」を判断し、バケットはバイト列を置くことだけを担う。

六つの製品ファイルの変更、そして誰も二度とやりたくない一回の移行。

## 譲れない三つの制約

- **オブジェクト名は内容であり、所有者ではない。** キーに owner を入れてはならず、作品 id も入れてはならない。そうでなければ重複排除が失われる。
- **削除は空操作。** セーブデータを一つ削除してもデータベースの所有権レコードを消すだけで、オブジェクトは残す——他に誰が参照しているか分からないからだ。物理 GC は今回やらない。ゴミを残すほうを選ぶ。
- **平文の上限は 32 MiB。** SHA256 で命名し、さらに provider が返すネイティブ SHA1 で照合する。同名だが内容が違う、あるいは読み終えたダイジェストが合わない場合は、いずれも失敗とし、決して上書きしない。

残りの二つはプロセス上のものだ。資格情報はメモリ内で受け渡し、ソースコードにもログにもローカルにも残さない。容量は明示的に null として報告し、偽のローカル空き容量をでっち上げない。

これらはコードを書く前にテストでまず赤くする。2 つの owner にまたがる同じバイト列は一度しかアップロードされない、owner を一つ削除しても共有本体は動かない、壊れた本体は上書きしない、不正な hash は IO の前に拒否される、scope や読み取り専用キーは最初のアップロード前に失敗する、429/503 は自動リトライしない、読み戻したダイジェストが不一致なら拒否する。37 項目の専用テストが通った後に境界を補い、22 項目のうちさらに 2 項目が赤くなった。CF が 401 を返したときに B2 認証を消しに行くべきではない。異常な非空メタデータをオブジェクト欠落と見なすべきではない。修正後は 42/42。

## 読み取り経路も計測する

書き終えた後、読み取りの並列度はダウンロードに食い尽くされた。そこで通常経路を一つ追加した。既に存在する CAS は固定 URL で Cloudflare 経由で読み、`Authorization` を付けず、Cookie も付けず、Range も付けず、クエリパラメータも加えず、リダイレクトも追わず、読み戻してサイズ、SHA256、ネイティブ SHA1 を照合する。ネイティブ SHA1 の証拠が欠けているバージョンはキャッシュを信じず、その正確な `fileId` でオリジンから一度読み、検証記録はこの版だけに紐づける。

プロセス内に 32 MiB / 128 件 / 60 秒の本体 LRU を置き、独立した Buffer を返し、ディスクには書かない。存在確認は毎回 B2 メタデータを引き直す——キャッシュにヒットしても、源側の古いバージョンかもしれないし、既に削除されているかもしれない。

オフラインのカウントで効果は見て取れる。既存オブジェクトの再読み取りは、CF 本体が 1 回、ネイティブダウンロードが 0 回。8 個の並列読み取りは 1 回のメタデータと 1 回の CF リクエストにまとまる。だがこれは合成リクエストにすぎず、オンラインの HIT 率とは呼べない。

## Cloudflare が先に道を塞いだ

初めて実際の経路で受け入れたとき、認証は 200、メタデータは 200、本体は 403 だった。

権限ではない。レシートに残った正確な CF-Ray イベントがはっきり書いている：`source=botFight`、`ruleId=bot_fight_mode`、`action=managed_challenge`。出口は IPv6 の `2a01:4f9:c013:773a::1` で、CF はこれをボットと見なし、チャレンジページを返した。`cf-mitigated: challenge`、`content-type: text/html`、本体は `Just a moment`。

回避策は三つあり、代償はそれぞれ違う：

- ゾーン全体の Bot Fight Mode を切る —— 影響が大きすぎる；
- ブラウザ UA を偽装する —— 明日には効かなくなるかもしれない；
- IP Allow を一つ追加する —— 最小だが、無料の IP Access allow は **IP 単位で `saop.cc` ゾーン全体に効く**ため、この IP の WAF もレート制限もまとめて飛ばしてしまい、リソース host だけに限定できない。

通常の WAF Skip は BFM に効かない、という点もそのとき確認した。最終的に IP Allow を一つ選び、ルール id をレシートに記録した。ロールバックはこの id を一つ消すだけだ。CF は IPv6 を展開形式で書き戻すため、元のスクリプトはテキスト比較で一度失敗し、POST を再送せず、別途読み取り専用の GET を立ててアドレスの等価性で検証し、前後のルール数 0 → 1 が一致した。

セキュリティ設定を変えること自体が「CF に触らない」という元の制約を超えていたので、明確な承認を待ってから動かし、その間プロダクションはずっと Windows のままだった。

## 中断したアップロードは再生しない

33 個のオブジェクト、1,994,672 バイトを移行し、単一並列、間隔 5 秒、429 か 503 で即座に止める。

そして次々とぶつかった：

- r1 は手前のファイルアクセス権限で失敗し、B2 リクエストは一度も送られなかった；
- r2 は最初のアップロードが 200、その後コールド認証と 5 秒の待機で 20 秒のタイムアウトを使い切った；
- r3 は認証を前倒しし、待機を操作の前に移し、6 項目通過後に `UND_ERR_SOCKET`；
- r4 は移行の HTTP に `Connection: close` を加え、20 項目通過、40 KB のオブジェクトを正確に読み戻して 200 の後、本体がタイムアウトした。
(This is part 1 of 2 of the same post.)

四回とも 429/503 は出なかった。各回で新しいタスク id に切り替え、旧タスクは再生しないが、**すでにアップロード済みのオブジェクトは既存の CAS で再利用**し、再送はしない。ここには必ず補わなければならない穴がある。以前に半分だけ送って止めたあの二つのオブジェクトは、200 のヘッダーしかなく、本文が完全である証明がなかった。のちに専用のゲートで正確な `fileId` に基づいて完全な読み戻しの受領証を補った。

タイムアウトは無闇に拡大するものではない。新たに追加した `operationTimeoutMs` は任意の整数で、範囲は 20〜120 秒、本番のデフォルトは依然として 20 秒で、移行タスクだけが明示的に 120 秒を与える。旧実装ではまず二件がレッドになり、新たな 44 項目の専用テストはすべてグリーンになった。

## 凍結は「ちょっと一時停止」ではない

実際の切り替えでは書き込みを止め、すべてを再確認する。短いウィンドウで。ウィンドウ内でやるべきこと：

- Windows 上で全量のハッシュを読み直し、今回の nonce を echo する——古いマニフェストに印を付け直すのではない；
- 41 個のオブジェクトをオフラインゲートに通し、本番 DB クローン内の参照カバレッジを照合する；
- マニフェストが既存のソースマニフェストの部分集合であることを確認する。

四回試してようやく確定した。本番のその回の凍結は 265.575 秒で、41 個のオブジェクト、94 ファイル / 1,996,140 バイト、76 行の owner、24 個の一意な hash、100 件の refs をカバーし、すべてが一致してから切り替えた。現役の compose を `save-cas-b2-20261115-r2` に差し替え、唯一変わったのは `WG_BLOB_STORAGE=b2-cas` だけ。

凍結の外側には二層の保護を置いた。420 秒の絶対 alarm と独立した Postgres watchdog だ。セッションとロック、二つの 0 の解放はすべて独立した確認に依存し、一つでも欠ければ停止する。

ついでに三つのプロトコルの穴も補った。`assertFreeze` はもともと空引数でデフォルト通過し、呼び出し側がチェッカーを渡し忘れても通ってしまっていた。missing-checker のケースを追加してまずレッドにし、次に明示的な関数の受け渡しを必須に変え、最後は 8/8 になった。

## ロールバックはデータベースを戻すだけでは済まない

これがこの回で最も重要な一条だ。

B2 に切り替えた後、そのまま `restore` で旧データベースに戻したり、旧 compose に戻したりすると、切り替え後に新たにアップロードされたオブジェクトを失う——データベースは過去に戻るが、バケットは戻らない。正しいやり方は逆だ。もう一度凍結し、新たに増えた B2 参照を hash に基づいて B2 から正確に読み戻し、Windows に書き戻し、完全に検証して、両者を再び揃えてから、旧バックエンドに切り替える。

ロールバックスクリプトにはいくつかの厳格な決まりがある。今回の凍結にある完全な SHA 証明を優先して再利用し、Windows に欠けているオブジェクトだけを B2 から読む。ロックを失うか 429/503 に遭えば即座に停止し、リトライしない。リリース前にはすでに完全な逆方向のリハーサルが exit 0 で一度あり、ロックの解放も確認済みだ。

何度かのリリース試行はさらに二つの教訓を残した。一度はパッケージに静的コピーが欠け、バージョン番号は変わったがモジュール本文が変わっておらず、ダイジェストゲートがその場で止めて自動的に旧コードへ戻し、現役設定の SHA は元の値に復元された。もう一度はチェッカーが信頼済みモジュール上の `private, no-store` を誤って「no-transform を含まねばならない」とみなした。どちらも成功とは数えず、元のログはすべて残してある。

## 受け入れの境界

リリース後は 31 点を約 15 分間モニタリングし、すべて通過、web/manager の fatal はいずれも 0。クラウドセーブの那群は Chromium、Firefox、WebKit でそれぞれ実際のアップロード、ダウンロード、履歴復元、冪等なコミット、二ページの WebSocket 権威イベントを一通り歩き、毎回新規に作成した合成 ID を使った。

それでもこうした「不算」は書いておく：

- 合成アカウントのみで、実際のユーザーのセーブは関与していない；
- ゲームソースの CDN は全行程で遮断し、四エンジンはロード画面のスモークのみ；
- 三カーネル四エンジンの完全マトリクスとは呼ばず、クリアとも呼ばない；
- WebKit のその回の集計スクリプトは依然として 3 ブラウザでアサートしており、実際には 1 項目しか走っていない。元の exit 1 は保持し、別途読み取り専用の集計を元 JSON の SHA に紐づけ、旧受領証は変更しない。

## 締めくくり

Windows の元のセーブ、旧 release、旧リソース、元アカウントはすべて残してある。移行の本文はメモリ上で Debian と Windows を通るだけで、Mac にも本番機にも落ちていない。

今いちばん覚えておくべきなのは CAS がどう重複排除するかではなく、計画に書き込んだあの一言だ。**逆方向の整合がなければ、直接ロールバックしてはならない。** 「ロールバック」をボタン扱いする移行は、切り替えたその瞬間にすでに借金を負っている。
