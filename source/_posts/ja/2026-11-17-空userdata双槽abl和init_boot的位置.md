両方の端末とも HyperOS 3（小米 13 は 309、Pad 6S Pro は 306）で、アンロックの手順を終えると画面にオレンジ色の警告、5秒の待機、そのあとシステムへ入る。ここまではすべて正常だ。

問題はその直後に来る。この記事で記録するのは3つの詰まりどころで、共通点は**エラーメッセージが指す方向と本当の原因が食い違っている**ことだ。

## 「Couldn't mount file system」はシステムの書き込み失敗ではない

アンロックは data を消すので、data パーティションは空でファイルシステムもまだ作られていない。recovery に初めて入ったとき、下部に出る赤文字が `Couldn't mount file system` だ。

system の書き込みが壊れたと誤解しやすく、それで system を焼き直しに戻りたくなる。だが不要だ。system は正常で、欠けているのは data のフォーマットだ。

対処は音量キーで `Wipe Data` を選び（recovery によっては `Format Data` / `Factory Reset` と呼ぶ）、電源キーで確定、もう一度確定してから `Reboot to system`。初回起動には数分かかる。

順序について覚えておくべき点が2つある：

- **フォーマットはシステムを焼いた後**に行う。焼く前にやらないこと——書き込みの過程で data が再び触られる可能性がある。
- コピーしたイメージのディレクトリを `sdcard` に残さないこと。フォーマットで一緒に消える。

## デュアルスロット：片方だけ書くのは後患を残す

この端末の `abl` には `_a` と `_b` の2つのスロットがある。

エンジニアリング用 abl を `abl_a` にだけ書くと、`abl_b` は公式版のままになる。デフォルトスロットが A のうちは違いが見えないが、一度ブートが B に切り替わると、2つのスロットの読み込みロジックは同じではなくなる。

ツールはデフォルトで2つ書くし、手で叩いても同じで、両方書いて最後に `sync`。書く前に `ls` してファイルがあることを確認する。

同じ理屈は以後のすべての「パーティションへ dd する」操作に当てはまる：**書き終えたら必ず現在のスロットを確認する**。A/B スロットは「バックアップ」ではなく、2台が交代で動く機械であり、あなたはそのうち1台しか直していない。

## 「OTA 後、A スロットが空」

ここが一番難しい。3つのものを同時に踏んでいるからだ。

システム更新がブートを B スロットへ切り替えたので、**現在のシステムから** `init_boot` を抜き出してパッチを当てる必要がある。抜き出す方法は2つあるように見えて、どちらも通らない：

- `fastboot fetch`：この bootloader は対応しておらず、`Device does not support fetch command` を吐く。
- `adb shell dd if=/dev/block/by-name/init_boot of=/sdcard/...`：shell が `disk` グループに属しておらず、読み出しは0バイトになる。

残る正攻法は2つだけ：6 GB の完全な公式パッケージを落として展開するか、もう一度一時 root を取って root 権限で `dd` により現在のスロットの中身を吸い出すか。後者はそんなに大きなパッケージを落とさずに済むが、代償として一時 root の一式をもう一度全部走らせることになる——しかも走らせ終えたらきれいな状態に再起動してからパッチを当てる必要がある。

ここは絶対に外せない判断がある：**現在のシステムは B スロットにあり、抜き出すのは `_b` の中身で、パッチも `init_boot_b` に焼かなければならない**。`_a` に焼いても何も表示されず、ただ効かないだけだ。

## boot か init_boot か

同じ問題が端末上で2つの答えになるのは、機種に独立パーティションがあるかどうかによる。

判断基準は汎用のもので、経験則ではない：

> あなたの端末に `init_boot` パーティションがあるなら `init_boot` を優先して直す。`boot` パーティションしかない場合にのみ `boot` を直す。

両方の端末とも `init_boot` を持つ。スマホもこのタブレットと同じ GKI デバイスだ——ramdisk は `init_boot` にあり、`boot` にはカーネルしか残っていない。

この構造が「どこに当てるか」を決める：`boot` に焼いても画面は点くし起動もする、カーネルは壊れていないからだ。だがパッチは ramdisk 内の init フックで読み込まれるので、`boot` に当ててもフックのない場所にイメージを放り込んだだけで、症状としては入れたのに相変わらず「未インストール」と表示される。2台ともこれでそれぞれ2往復を無駄にした（次回詳述）。

## 状態を確認する2つのコマンド

「良さそうに見える」より信頼できる判断：

```sh
adb shell getprop ro.boot.verifiedbootstate   # orange = アンロック済み
adb shell getprop ro.boot.flash.locked        # 0 = 未ロック
adb shell getprop sys.boot_completed          # 1 = 已正常开机
```

バージョンが合っているかは設定画面の「アンロック済み」の行ではなく、`ro.build.display.id` か設定内の完全なバージョン番号で見る。

## まとめ

3つの詰まりどころは最後には同じ一言に戻る：**まず今どのスロットにいて、どのパーティションを触るのかをはっきりさせ、それからどのコマンドを使うか決める。**

`Couldn't mount file system` は壊れたシステムに見え、デュアルスロットは「どうせ一緒に書かれる」に見え、`fastboot fetch` は「コマンド1つの話」に見える。3つの錯覚の共通の結果はどれも、5分の操作を一から焼き直す作業に変えてしまうことだ。

技術的ではないが同じくらい重要な点がもう1つある：アンロックして焼き終えてから数日のうちは**システム更新を押すな**。OTA はパッチを上書きし、スロットを切り替え、ようやく把握したスロットをもう一度ひっくり返す。しかもメジャーバージョンは検証済みの方法をかき乱す。

## よくある質問

**Q：アンロック後 recovery に入ると `Couldn't mount file system` と出るが、システムの書き込みが壊れたのか？**
違う。アンロックが data を空にし、ファイルシステムがまだ作られていない。音量キーで `Wipe Data` を選んで data をフォーマットし再起動すればいい。system は正常だ。

**Q：`abl_a` と `abl_b` は両方焼く必要があるのか？**
両方だ。片方のスロットだけ書くと、もう片方は公式版のままで、アンロック後にスロットが切り替わった途端に2つのスロットのブートが不一致になる。

**Q：`fastboot fetch` がサポートされていない場合、現在のスロットの `init_boot` をどうやって取り出せばいいですか？**
方法は2つあります。完全な6 GBの公式カード書き込みパッケージをダウンロードして展開するか、もう一度一時rootを取得してroot権限で`dd`し、現在のスロットの内容を取り出します。取り出した後は必ず同じスロットに書き戻してください。
