Pad 6S Pro（`sheng`）をアンロックし、公式 306 に焼き戻し、root を入れた後、「いじれる機械がもう一台増えた」だけでなく、ノート PC 的な仕事もさせたくなった：LibreOffice、ターミナル、ブラウザ、お絵かき。

まず何なのかをはっきりさせておく：**これは chroot であって、ネイティブ Linux ではない。** Android がずっと下で動いていて、メモリを奪い、CPU を制限し、グラフィックは直接出力ではなく X11 転送を通る。軽い事務作業ならなんとかなるが、4K 編集や大規模ビルドは期待しないほうがいい。

## 三つの道の取捨

- **ネイティブデュアルブート**（B スロットに Linux を入れる）：性能は最高だが、スロットを触る必要がある。アンロックしたばかりで公式システムを焼いた直後に、スロット切り替えのリスクを別途計上するのは割に合わない。
- **Fedora + KDE**：2026 年、実際にやっている人はいるが、状態は「実験」だ——リポジトリは GitHub Actions でその場でビルドする `rootfs.img` 方式で、作者は十時間前までまだ手を入れていた。インストールは ISO を一本落とすだけの話ではない。
- **Termux + chroot**：すべて `/data` の中で完結し、パーティションに触れず、失敗したらディレクトリを消してやり直せばいい。`reboot` すら要らないかもしれない。

三つ目を選んだ。Debian 13 のイメージには KDE Plasma が入っており、`proot-distro` は展開器として一度使うだけで、以降は proot を通らない。

## 成否を分ける三つの罠

この三点を知らない人は必ず踏むし、踏んだときの症状はどれも「性能が悪い」にそっくりだ。

**一、Mesa は必ず差し替える。** Debian 標準の Mesa は DRM の `msm` ドライバを使うが、Android カーネルは `/dev/kgsl-3d0` しか公開していない。公式 Mesa をそのまま入れると `llvmpipe` のソフトウェアレンダリングになり、KWin はクリックにも反応しないほど固まる。[lfdevs/mesa-for-android-container](https://github.com/lfdevs/mesa-for-android-container) の kgsl ビルド（Adreno 740 対応、まさに chroot 用）に差し替える必要がある。入れたら `apt-mark hold` し、さらに `glxinfo -B` で renderer が `FD740 / Adreno (TM) 740`、OpenGL 4.x であることを確認する。`llvmpipe` しか残っていなければ失敗だ。

**二、chroot で X を起動するには作法がある。** `setenforce 0`、`TMPDIR` は chroot の `/tmp` を指し、`XKB_CONFIG_ROOT` は chroot の xkb を指す。そして X サーバーは `termux-x11` コマンドではなく `app_process` で起動する。一つでも欠けると黒画面か xkbcomp のエラーになる。

**三、Termux:X11 は sharedUid の APK を使う。** 使わないと、Android は「X11 が前面、Termux が背面」という理由で Termux の CPU を絞り、デスクトップはあからさまにフレーム落ちする。代償は、GitHub 署名の Termux しか受け付けないこと。F-Droid 版は署名が異なり、同じ UID では入れられない。

## root が与えるのは権限であって、スケジューリングの重みではない

これは最も誤解しやすい。

root があってもデスクトップが滑らかになるわけではない。速度制限と root は別の仕組みだ：

- `system_server` は「このアプリが今見えているか」に応じて、プロセスツリー全体を `top-app` / `foreground` / `background` / `cached` の cgroup に押し込む。`su` で出てきたプロセスも Termux の子プロセスのままで、Termux のグループを継承し、`su` はそれを並べ直してはくれない。
- 具体的な絞り方は `cpuset.cpus`（background/cached は小さいコアに押し付けられる）、`cpu.weight`（重みが一桁違う）、`cgroup.freeze`（cached に入って十秒でプロセスツリー全体が凍結される）。Termux が凍れば、その下にぶら下がる X サーバーも一緒に凍り、デスクトップは固まる。

そこで `05-pin-priority.sh` を一つ足した：`cgroup.freeze` を解凍し、`cpu.weight` を 1000 に上げ、`cpuset.cpus` で全コアを開放し、Termux と X サーバーに `oom_score_adj=-900`、`renice -10`、`taskset` を打ってコアを固定する。

**だがこれはパッチであって特効薬ではない。** `system_server` は前面/背面を切り替えるたびにこれらのファイルを書き換えるので、一度離れて戻ればほぼ元通りになり、再実行が必要だ。これが効くのは CPU を奪えるかどうかだけで、あなたが離れた瞬間に freezer がプロセスを凍らせるのは止められない。

最初からグループを落とさない本当の方法は sharedUid の APK で、代償は前述のとおりだ。

## 作業前の準備

- Termux は GitHub Releases か F-Droid から入れる。Google Play は使わない（更新が止まっている）。Termux:X11 は nightly から落とす。
- 両方のアプリの省電力設定を「無制限」にする。
- 15 GB 以上を空けておく（KDE のインストール後は約 4 GB）。
- USB デバッグを有効にしておく。なにかあったら `adb` で救出する。
- `su` できることが必要。

## まとめ

デスクトップは起動した。Chromium も開けるし、LibreOffice も開けるし、ターミナルも使える。代償は、他のアプリに切り替えて戻ると一瞬固まること、バックグラウンドに長く置くと凍結されることだ。

それは「緊急時に使えるタブレット」になったのであって、ノートPCではない。この前提を先に置いておけば、残りは許容できる操作コストでしかない。

## よくある質問

**Q：Pad 6S Pro にネイティブ Linux や Fedora は入りますか？**
入りますが、成熟度はかなり違います。ネイティブのデュアルブートは B スロットを触る必要があります。sheng 上の Fedora はまだ実験室状態で、自分で GitHub Actions を回してイメージを出す必要があります。Debian 13 の chroot が、デフォルトで結果を出せる唯一の道です。

**Q：これは root 必須ですか？**
必須です。chroot は `/dev`、`/proc`、`/sys` をマウントし SELinux を切り替える必要があり、`su` なしでは無理です。

**Q：なぜデスクトップはこんなにカクつくのですか？**
まず Mesa を確認してください。`glxinfo -B` で renderer が `llvmpipe` なら、まだソフトウェアレンダリングのままで、kgsl 版 Mesa が入っていません。正しく入れてもまだカクつくなら、Android の cgroup が制限をかけています——`cpuset`、`cpu.weight`、`cgroup.freeze` はいずれも root とは無関係で、継続的に補っていく必要があります。
